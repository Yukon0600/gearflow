# 应收应付与收付款

## 为什么做

进销存只有单据不够用——实际经营里「卖了没收到钱」「进了货没付钱」才是关键。所以补一层往来结算：

```
应收 = Σ 销售单金额 − Σ 销售退货金额 − Σ 已收款
应付 = Σ 采购单金额 − Σ 采购退货金额 − Σ 已付款
```

按往来单位（客户/供应商名称）汇总，余额为正表示对方还欠我（应收）或我还欠对方（应付）。

## 数据模型

`payments` 表：

| 字段 | 说明 |
| --- | --- |
| `direction` | `in` 收款 / `out` 付款，带 CHECK 约束 |
| `partner` | 往来单位名称，与单据里的 partner 对应 |
| `amount` | 正整数（分），带 `CHECK(amount > 0)` |
| `method` | cash / wechat / alipay / bank / other |
| `orderId` | 可选关联单据，填了会校验存在性 |
| `note` / `createdAt` / `createdBy` | 备注、时间、经办人 |

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/reconcile` | 应收与应付汇总（含每个单位的开单、退货、已收付、余额） |
| GET | `/api/payments?page&size&direction&partner` | 收付款流水，分页 |
| POST | `/api/payments` | 登记收付款 |

**核心校验**：登记金额不能超过该单位当前余额，超出直接 409，并提示真实余额。这样不会因为手滑多记一笔收款，把账做成负数。

权限：查看（GET）店员即可；登记（POST）需要店长及以上。收付款属于财务动作，店员只负责开单。

## 已知边界

- 退货单目前允许独立于销售单存在。如果给一个从没买过的客户登记退货，应收会变成负数——界面上标为「多退」，并以橙色显示，不参与应收合计（合计只累加正数）。
- 没有「预收款/预付账款」概念，也没有账期和信用额度。
- 收付款不能撤销，只能反向再记一笔（暂未提供冲销功能）。

这三点是这一层目前的边界，论文里可以当作「后续可扩展方向」写。
