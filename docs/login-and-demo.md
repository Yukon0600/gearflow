# 登录与演示数据

在项目根目录运行 `npm run dev`，访问 http://localhost:5173。

本地初始账号：`admin`，初始密码：`GearFlow@2026`。首次建立账号时可以用服务器环境变量 `GEARFLOW_ADMIN_PASSWORD` 指定其他初始密码；已有账号不受该环境变量更改影响。目前是单工作区管理员登录，没有注册、角色管理或找回密码功能。

密码以随机盐 + scrypt 散列保存。服务端在 SQLite 保存会话令牌的 SHA-256 摘要，浏览器通过 HttpOnly、SameSite=Strict Cookie 保存随机令牌，会话有效期 8 小时；刷新和服务重启保留未过期会话。退出后服务端立即撤销会话。除健康检查和登录/退出接口外，业务接口要求有效登录；连续错误登录按来源 IP 限制每分钟 10 次。HTTPS 部署时设置 `GEARFLOW_SECURE_COOKIE=1`。

登录相关接口：`POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/logout`。前端收到业务接口 401 时返回登录页。

演示库包含 36 件商品：处理器 5、显卡 5、内存 5、存储 5、主板 5、外设 6、电源/散热 5；客户 6、供应商 6。部分商品库存偏低或为零，可演示预警与缺货状态。客户和供应商使用虚构名称、地址与联系人，不填写真实电话号码；备注明确标记为测试数据。

扩充数据通过 `demo_migrations` 的 `catalog-v2` 标记只运行一次。按 SKU、单位类型及名称去重，不覆盖原商品价格、库存或已有单位资料；新增商品同时建立期初库存流水。已运行的旧数据库会自动补齐本次新增记录。数据来自数据库，由 `/api/workspace` 返回前端，不是前端写死列表。

演示业务批次 `business-activity-v1` 另补 24 张采购入库单、24 张销售出库单、12 张库存盘点单。采购和销售每单 3 行商品，每个演示客户和供应商各关联 4 笔交易；盘点包含账实一致、盘盈和盘亏情形。所有单据通过现有业务方法确认，金额、库存与流水同步变化，备注均标记「演示数据」。使用实际生成时间，不倒填历史日期，以保持既有库存流水顺序。整个批次与迁移标记在同一事务中提交，失败回滚，重启不重复导入。原有业务记录保留，商品余额会随新增演示交易调整。

验证：`npm run test:server` 检查密码散列、会话过期、注销、示例数据重启幂等性及库存事务；`npm run test:e2e` 检查登录/退出、接口保护、全品类数据、原有业务流程和移动端。测试使用隔离数据库，不向日常数据库写入测试订单。
